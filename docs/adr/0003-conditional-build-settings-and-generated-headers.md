# ADR 0003: Conditional build settings and generated headers

- Status: Proposed
- Date: 2026-10-01
- Issue: #22 (Tier 3)

## Context

Tier 3 of #22 (LLVM, SerenityOS, Carbon) has been deferred because cmod
lacks two things. A manifest cannot say "these files and flags only on this
platform or in this profile", and it cannot produce a header from a template
at build time. The `[build]` table has static `sources`, `exclude`,
`include_dirs` and `extra_flags`, and nothing else.

Tier 1 and 2 got around both. Catch2's port commits a pre-generated
`catch_user_config.hpp`. abseil's port excludes the Windows-only files
outright, which works only because nobody builds it for Windows. Neither
trick works for LLVM. Its generated headers record the target and the build
configuration, so a committed copy is right for one host and one profile.

### What exists today

- `cmod-core/src/manifest.rs` already has a `cfg(...)` evaluator, `eval_cfg`.
  It supports `target_os`, `target_arch`, `target_family`, `target_env`,
  `unix`, `windows`, `all`, `any` and `not`. Its only use is
  `[target.'cfg(...)'.dependencies]`.
- `eval_cfg` returns `false` for a key it does not know. A typo such as
  `cfg(taget_os = "linux")` silently drops the dependency.
- `target_arch` is the first triple component and `target_os` the third. On
  Apple Silicon the default triple is `arm64-apple-darwin`, so
  `target_arch = "aarch64"` is false and `target_os = "macos"` is false.
- `TargetSpec` has only `dependencies`. Serde ignores other keys, so main
  accepts `[target.'cfg(...)'.build]` and does nothing with it (shown below).
- `cmod resolve --target <triple>` filters `[target.*.dependencies]` before
  locking. The same manifest gives a different `cmod.lock` depending on
  `--target`, and a different one again with no `--target`.
- Neither the incremental state (`BuildState::needs_rebuild`) nor the cache
  key (`CacheKeyInputs`) covers `#include`d headers. Each hashes the
  translation unit's own source, the flags fingerprint, and its dependency
  nodes' outputs. With the `llvm-abibreak` fixture below and
  `abi-breaking.h` generated by `cmake -P`:

  | Step | `LLVM_ENABLE_ABI_BREAKING_CHECKS` | Summary | Symbol in the archive |
  |---|---|---|---|
  | `cmod build` | 1 | 1 compiled | `EnableABIBreakingChecks` |
  | `cmod build` | 0 | 1 up-to-date | `EnableABIBreakingChecks` (stale) |
  | `cmod build --force` | 0 | 1 cached | `EnableABIBreakingChecks` (stale) |
  | `cmod --no-cache build --force` | 0 | 1 compiled | `DisableABIBreakingChecks` |

  `--force` skips the incremental state, but the cache key is the same, so
  the stale object comes back from the cache. Any project with the same
  source file and flags would get that object too, including through a
  remote cache. This is an existing bug with hand-written headers.
  Generated headers would hit it on every configuration change, so the
  design below has to work around it.

## Fixtures

Both are slices of LLVM 19.1.7 `llvm/lib/Support`, fetched by commit
(`cd708029e0b2869e80abe31ddb175f7c35361f90`). LLVM is the Tier 3 project the
other two build on, and `Support` is the bottom of its library graph.

| Fixture | Files | Needs | Fails on main with |
|---|---|---|---|
| `llvm-abibreak` | `ABIBreak.cpp`, `abi-breaking.h.cmake` | generated header, profile predicate | `'llvm/Config/abi-breaking.h' file not found` |
| `llvm-blake3` | 8 `.c` + 3 headers from `BLAKE3/`, `Compiler.h`, `llvm-config.h.cmake` | generated header, platform predicate on sources and defines | `'llvm/Config/llvm-config.h' file not found` |

`llvm-abibreak` is the acceptance fixture: one translation unit and one
template. `ABIBreak.cpp` includes `llvm/Config/abi-breaking.h`, which CMake
writes from `abi-breaking.h.cmake` with `configure_file`. The value it
writes, `LLVM_ENABLE_ABI_BREAKING_CHECKS`, follows `LLVM_ENABLE_ASSERTIONS`,
which LLVM turns on for Debug builds. So the header's content depends on the
profile.

`llvm-blake3` is the platform case. LLVM's `BLAKE3/CMakeLists.txt` builds
`blake3.c`, `blake3_dispatch.c`, `blake3_portable.c` and `blake3_neon.c`
everywhere. On x86-64 it adds assembly files. On every other architecture it
adds `-DBLAKE3_NO_AVX512 -DBLAKE3_NO_AVX2 -DBLAKE3_NO_SSE41 -DBLAKE3_NO_SSE2`.
The `blake3_{sse2,sse41,avx2,avx512}.c` intrinsics files are never built.

### What `llvm-blake3` hits next

To see past the first error I generated `llvm-config.h` by hand with CMake's
own `configure_file` (`cmake -P`, arm64 macOS values). The build then fails
on the x86 intrinsics files (first lines, then the last line):

```
    Building llvm-blake3 (debug)
    Compiled ./llvm-blake3/src/blake3.c
In file included from ./llvm-blake3/src/blake3_avx2.c:3:
/opt/homebrew/Cellar/llvm/23.1.0/lib/clang/23/include/immintrin.h:14:2: error: "This header is only meant to be used on x86 and x64 architecture"
...
error: build failed: failed to compile: ./llvm-blake3/src/blake3_avx2.c
```

Adding a static `exclude` for the four intrinsics files makes the arm64
build pass (`Finished .../libllvm-blake3.a`, 4 modules). That manifest is
wrong for x86-64: `blake3_dispatch.c` calls `blake3_hash_many_sse2` and the
others unless `BLAKE3_NO_SSE2` and friends are defined, and nothing would
define them. I read that from the source and did not build it on x86-64.
No static manifest is right for both.

Adding the block this ADR proposes to the same manifest changes nothing on
main:

```toml
[target.'cfg(not(target_arch = "x86_64"))'.build]
exclude = ["blake3_sse2.c", "blake3_sse41.c", "blake3_avx2.c", "blake3_avx512.c"]
extra_flags = ["-DBLAKE3_NO_AVX512", "-DBLAKE3_NO_AVX2", "-DBLAKE3_NO_SSE41", "-DBLAKE3_NO_SSE2"]
```

main parses it, ignores it, and fails on `blake3_avx2.c` with the same
`immintrin.h` error.

## Decision

### 1. One predicate language: `cfg(...)`

Keep the existing `cfg(...)` grammar and evaluator. Make it stricter and
give it two kinds of key.

Platform keys come from the target triple:

| Key | Values | Notes |
|---|---|---|
| `target_arch` | `x86_64`, `aarch64`, `arm`, `x86`, `riscv64`, ... | `arm64` is normalised to `aarch64` |
| `target_os` | `linux`, `macos`, `windows`, `freebsd`, ... | `darwin*` is normalised to `macos`; version suffixes are dropped |
| `target_family` | `unix`, `windows` | as today |
| `target_env` | `gnu`, `musl`, `msvc`, ... | as today |
| `unix`, `windows` | (bare) | as today |

Config keys come from the build:

| Key | Values | Source |
|---|---|---|
| `profile` | `debug`, `release` | `--release` |
| `compiler` | `clang`, `gcc`, `msvc` | the root compiler (ADR 0002) |
| `feature` | any declared feature | `--features`, `default` |

Rules:

- An unknown key, an unknown bare word, or a `feature` value not declared
  in `[features]` is a manifest error at load time. It is not `false`.
- `target_arch = "aarch64"` and `target_os = "macos"` match
  `arm64-apple-darwin`. `target_os = "darwin"` keeps matching for one
  release with a deprecation note, because manifests may already use it.
- Config keys are allowed in `build` and `configure` blocks only. In a
  `dependencies` block they are an error. Optional dependencies stay under
  `[features]` and `dep:`, so the set of packages to fetch never depends on
  the profile or the compiler.

### 2. Manifest syntax: `[target.'cfg(...)']` grows `build` and `configure`

`TargetSpec` gets two more sub-tables next to `dependencies`:

```toml
[build]
type = "static-lib"
include_dirs = ["include"]

[target.'cfg(not(target_arch = "x86_64"))'.build]
exclude = ["blake3_sse2.c", "blake3_sse41.c", "blake3_avx2.c", "blake3_avx512.c"]
extra_flags = ["-DBLAKE3_NO_AVX512", "-DBLAKE3_NO_AVX2", "-DBLAKE3_NO_SSE41", "-DBLAKE3_NO_SSE2"]

[target.'cfg(windows)'.build]
sources = ["src/windows"]
```

- A target `build` block may only set `sources`, `exclude`, `include_dirs`
  and `extra_flags`. Each is appended to the base `[build]` value. `type`,
  `optimization`, `lto` and the rest are an error in a target block, so a
  predicate never changes what kind of artifact the package is.
- Matching blocks are applied in the order of their key strings, which is
  how the manifest's `BTreeMap` already iterates. The result does not
  depend on how the file is laid out.
- A file is compiled if it is under a base or matching `sources` directory
  and no base or matching `exclude` pattern matches it.
- `cmod build --verbose` lists which `cfg` blocks matched.

The table keeps the `target` name even for `cfg(profile = "debug")`. One
table and one grammar is easier to learn than a second table with the same
rules, and it is already parsed.

### 3. Generated headers: `[configure]` and `[[generate]]`

```toml
[configure]
LLVM_ENABLE_ABI_BREAKING_CHECKS = false
LLVM_ENABLE_REVERSE_ITERATION = false

[target.'cfg(profile = "debug")'.configure]
LLVM_ENABLE_ABI_BREAKING_CHECKS = true

[[generate]]
template = "include/llvm/Config/abi-breaking.h.cmake"
output = "llvm/Config/abi-breaking.h"
```

- `[configure]` holds variables: booleans, integers or strings. Matching
  `[target.*.configure]` blocks override base values. If two matching
  blocks set the same variable to different values, that is an error, so
  the result does not depend on block order.
- Each `[[generate]]` entry turns one template into one header. The syntax
  is CMake `configure_file`: `#cmakedefine VAR ...`, `#cmakedefine01 VAR`,
  `${VAR}` and `@VAR@`. That is what LLVM, and most projects that would
  migrate with `cmod migrate cmake`, already have. cmod implements the
  substitution itself. It does not run CMake or any other program.
- A template that names a variable `[configure]` does not define is an
  error that lists every missing name at once. CMake treats an undefined
  variable as false. cmod does not, because a silently false
  `LLVM_ON_UNIX` is the bug this ADR exists to prevent.
- `output` is relative to a generated include directory,
  `build/<profile>/gen/include/`. Nothing is written into the source tree.
  That directory goes on the package's include path before `include_dirs`,
  so a stale checked-in copy cannot shadow the generated one.
- A dependency's generated include directory is exported to its consumers,
  the same way its `include_dirs` are. LLVM's `abi-breaking.h` is a public
  header.

Running a program to produce a file (LLVM's `llvm-tblgen`, SerenityOS's IPC
and protocol generators) is not part of this ADR. It needs host-tool
`build-dependencies`, which are parsed but unused today, and a sandbox
story. It gets its own ADR. This one covers the template case, which is
what `Support` needs first.

### 4. How a generated header becomes a build-graph node

- `NodeKind` gets a `Generate` variant. One node per `[[generate]]` entry.
  Its inputs are the template's content hash and the resolved `[configure]`
  values, serialised sorted by name. Its output is the header.
- Generate nodes run first, before source scanning. Clang's dependency
  scan preprocesses each file, so the headers must exist before the module
  graph can be built.
- Every compile node in the package gets an edge to every Generate node in
  the package. cmod does not know which file includes which header (see
  Context), so the edge is coarse. Changing one generated header rebuilds
  the whole package. That is slower than it needs to be, and correct.
- The header is written to a temporary file and renamed into place, and
  only when its content changed. An unchanged header keeps its mtime and
  hash, so dependants do not rebuild.

### 5. Resolver and lockfile

- The resolver locks the union of `[dependencies]` and every
  `[target.*.dependencies]` block, whatever `--target` says. This is
  Cargo's rule. `cmod build` then builds only the locked packages whose
  predicates match the build's target.
- `--target` on `cmod resolve` no longer changes `cmod.lock`.
- The lockfile format does not change. No new fields.
- `build`, `configure` and `generate` blocks are never seen by the
  resolver. They only affect the build of the package that declares them.

### 6. Build fingerprint and cache keys

The predicates do not enter any key. What they select does, through inputs
that are already keyed:

- Selected sources: each translation unit is its own node with its own key.
  A file that a predicate drops has no node.
- `extra_flags` and `include_dirs` from matching blocks become backend flags.
  `CompilerBackend::fingerprint` already includes `extra_flags`, and the
  fingerprint is part of every cache key.
- Generated headers: the Generate node's output hash goes into each compile
  node's `dependency_hashes`, through the edges in section 4.
  `CacheKey::compute` and `BuildState::needs_rebuild` already hash
  dependency outputs.

So:

- **The key format does not change.** `CacheKey`, `CacheKeyInputs`, the
  fingerprint layout and the cache directory layout stay as they are.
- **A package that uses none of the new tables keeps its keys.** No flags,
  sources or edges change for it. That is every package in cmod-ecosystem
  today: all nine ports' `cmod.toml` on `cmod-support` have an empty
  `[target]` table and nothing else from this ADR.
- **A package that adopts them gets new keys for its affected nodes,** once.
- Writing the same predicate two ways (`cfg(unix)` and
  `cfg(target_family = "unix")`) can change the block order and so the flag
  order. That costs one cold build and is never wrong.

## Consequences

- **`cmod.toml` gains tables:** `[target.*.build]`, `[target.*.configure]`,
  `[configure]` and `[[generate]]`. `rfc_unified_cmod_schema.md` is updated
  when this is implemented, not in this PR.
- **Older cmod does not reject the new tables.** Serde ignores unknown keys.
  A manifest with `[[generate]]` fails loudly on an older cmod, as the
  fixtures show. A manifest with `[target.*.build]` builds on an older cmod
  without its conditional flags, which can be silently wrong. I do not
  have a fix for that short of a minimum-cmod-version field, which older cmod
  would also ignore.
- **Unknown `cfg` keys become errors.** A manifest that relied on a typo
  evaluating to `false` stops loading. That is the point. It is still a
  breaking change for that manifest.
- **The lockfile content changes** for a manifest with
  `[target.*.dependencies]` that was resolved for one target. The lock gains
  the other targets' packages. The format is the same.
- **The module DAG gains Generate nodes** and edges from them. Module units
  and their import edges do not change.
- **SBOM output changes only where the lockfile does.** `generate_sbom`
  reads the manifest and `cmod.lock`, so a manifest whose lock gains other
  targets' packages (section 5) gets them in its SBOM too. Generated headers
  are build outputs and are not listed.
- **Signing does not change.** It signs the same artifacts as before. A
  generated header is an input to them, not one of them.
- **Header tracking stays broken** for hand-written headers, in both the
  incremental state and the cache key (see Context). That is a separate fix
  (per-file include lists from `-MD` depfiles or the scanner), and the coarse
  edges here should be narrowed once it lands.
- **Out of scope:** assembly sources (`.S`, `.asm`; BLAKE3's x86-64 path
  needs them, and cmod does not discover them), per-file flags (the
  intrinsics files need `-msse4.1` and similar), and running generators.

## Acceptance for the implementation

Once this is accepted, the implementation is done when:

1. `llvm-abibreak` builds in debug and release with the `[configure]` and
   `[[generate]]` above. The debug archive defines `EnableABIBreakingChecks`
   and the release archive defines `DisableABIBreakingChecks` (`nm`).
2. `llvm-blake3` builds on macOS arm64 and Linux x86-64 from one manifest,
   with `llvm-config.h` generated and the target block above (x86-64 using
   `BLAKE3_NO_*` until assembly sources are supported).
3. Changing a `[configure]` value rebuilds the package's compile nodes, and
   changing nothing rebuilds nothing.
4. `cmod.lock` for a manifest with `[target.*.dependencies]` is the same
   with and without `--target`.
